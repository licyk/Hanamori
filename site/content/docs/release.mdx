[Release 工作流](https://github.com/licyk/Hanamori/blob/main/.github/workflows/release.yml) 统一发布 GitHub Release 和 `hanamori` crate。推送 `v*` 标签时发布到两个渠道；手动运行时可以选择标签和发布渠道。普通 main 推送与网站构建不发布版本。

## 更新版本与创建标签

在工作区或其成员包目录中使用仓库自带的 `xtask`：

```sh
cargo xtask bump          # 默认 patch：0.1.1 -> 0.1.2
cargo xtask bump minor    # 另一种选择：递增 minor，patch 归零
cargo xtask bump major    # 另一种选择：递增 major，minor 和 patch 归零
```

选择其中一种递增方式。命令更新 `Cargo.toml` 的 `workspace.package.version`，并由 Cargo 同步 `Cargo.lock` 中的工作区包版本，保留已锁定的依赖版本。命令不会提交修改或创建标签。先提交版本修改，再创建标签：

```sh
git add Cargo.toml Cargo.lock
git commit -m "chore: bump version"
cargo xtask tag --push
```

`cargo xtask tag` 在 `HEAD` 创建带注释的 `v版本号` 标签，默认不推送。默认版本来自当前工作区，而非已有 Git 标签中的最高版本。也可显式指定版本，例如 `cargo xtask tag 0.1.2 --push`；指定值必须与工作区版本一致。已跟踪文件的修改必须先提交，已有标签不会被覆盖。

`--push` 仅将刚创建的标签推送到 `origin`，触发两个发布渠道。推送失败时保留本地标签，并输出可重试的 `git push` 命令。

## 选择标签与渠道

在 Actions 中选择 **Release → Run workflow**，使用 `main` 上的工作流：

| 输入 | 含义 |
| --- | --- |
| `tag` | 可选的既有 `v*` Git 标签，例如 `v0.1.0`。留空时按 Git 版本排序选择最高的 `v*` 标签，而非按标签创建时间或 GitHub Release 时间选择。 |
| `target` | `all`（默认）同时发布两个渠道；`github` 只发布 GitHub Release；`crates-io` 只发布 crate。 |

```sh
# 自动选择最新标签，发布到两个渠道
gh workflow run release.yml --ref main

# 自动选择最新标签，只发布 GitHub Release
gh workflow run release.yml --ref main -f target=github

# 指定已有标签，只发布 crates.io
gh workflow run release.yml --ref main -f tag=v0.1.0 -f target=crates-io
```

工作流不会创建标签。没有 `v*` 标签、指定标签不存在，或标签版本与对应源码的 Cargo 版本不一致时，发布停止。推送标签触发时使用该标签；手动运行的 `tag` 输入优先。

## 检查、构建与发布

1. 更新工作区版本和由 Cargo 生成的锁文件，创建指向目标源码的 `v*` 标签。
2. Release 获取全部标签，解析所选标签的提交，并校验该提交的 Cargo 包名称、版本和二进制目标。
3. 复用 [CI 工作流](https://github.com/licyk/Hanamori/blob/main/.github/workflows/ci.yml)和 [Installers 工作流](https://github.com/licyk/Hanamori/blob/main/.github/workflows/installers.yml)，分别验证同一提交的 Rust 代码和安装脚本。Rust 检查包括格式、模块架构和测试；安装检查包括 Linux 参数与元数据，以及原生 Windows 安装。Windows 使用 release 配置及 `x86_64-pc-windows-msvc` / `aarch64-pc-windows-msvc` 目标。
4. 检查通过后，所选渠道分别从同一提交构建和发布。普通分支 CI 不响应标签推送；一次 Release 的两个渠道共用检查，不再分别运行 `cargo test`。
5. GitHub 渠道分别在 Windows x64 和 `windows-11-arm` 构建 `hanamori-x86_64-pc-windows-msvc.exe`、`hanamori-aarch64-pc-windows-msvc.exe` 及各自同名 ZIP。ZIP 内为 `hanamori.exe`；四个资产都验证 GitHub 报告的 SHA-256 digest。
6. crates.io 渠道运行 `cargo publish --locked`，保留包内源码的编译验证，仅发布 `hanamori`，不发布 `hanamori-test-support` 或 `xtask`。

两种发布渠道在共享检查通过后独立执行。某个渠道失败时，可手动选择尚未发布的渠道和同一标签重试。手动发布旧标签时，检查和构建使用该标签源码，而不是工作流所在的 main 源码。

成功的 CI、网站上线或某个渠道发布成功，都不代表另一渠道已经发布。GitHub Release 完成后，还应确认用户能够下载对应资产。下载页和自我更新按上述资产名称匹配版本；下载页查询公开 API，不包含 Token。

## crates.io 凭据与重试

在仓库的 Actions Secrets 中配置 `CARGO_REGISTRY_TOKEN`，使用有权发布 `hanamori` 的 crates.io API token。首次发布需要创建 crate 的权限；后续发布需要该 crate 的发布权限。

发布前可在本地执行 `cargo publish --locked --registry crates-io -p hanamori --dry-run`，验证包内源码能够编译而不上传。crates.io 已发布的版本不能覆盖；如果 crate 已发布、只需补发 GitHub 资产，请选择 `target=github`。
