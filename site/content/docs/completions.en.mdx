Hanamori generates completion scripts from the current build's command definitions. Tab completes public commands, nested subcommands and options. Generation needs no installed toolchain, network access or manager configuration.

## Enable with shell initialization

```sh
hanamori shell init --completions
```

Omitting `--shell` detects the calling shell; you can explicitly select `powershell`, `bash` or `zsh`. As with normal initialization, use `--profile PATH` or `--shell-executable PATH` to select the startup file/runtime, and `--dry-run` to preview changes.

Open a new terminal or follow the printed profile reload instruction. The startup block stores a loader that generates completion from the executable on each startup, so new sessions use the updated command definitions after an upgrade. Normal `shell init` does not enable completion. Keep `--completions` when updating the managed block; omitting it switches the block back to loading only the hook.

In Zsh, place the Hanamori startup block after `compinit` or your framework's completion initialization. If initialization is missing, Hanamori prints a hint and skips completion while keeping the toolchain hook usable. It does not run `compinit` for you.

## Enable in this session only

PowerShell:

```powershell
hanamori env --completions --shell powershell --output ./hanamori-init.ps1
if ($LASTEXITCODE -eq 0) { . ./hanamori-init.ps1 }
```

Bash:

```bash
hanamori env --completions --shell bash --output ./hanamori-init.sh && . ./hanamori-init.sh
```

Zsh:

```zsh
# Skip this initialization if your framework already calls compinit.
autoload -Uz compinit
compinit
hanamori env --completions --shell zsh --output ./hanamori-init.zsh && . ./hanamori-init.zsh
```

These commands load both the `use/deactivate` hook and completion. To load completion alone, replace `env --completions` with `completions`; it neither installs an environment hook nor activates a toolchain.

## Generate a standalone script

```sh
hanamori completions
hanamori completions --shell bash
hanamori completions --shell zsh --output ./hanamori-completion.zsh
hanamori completions --shell powershell --output ./hanamori-completion.ps1
```

Without `--shell/-s`, detection selects the calling shell or asks you to specify it. Without `--output/-o`, stdout contains only the registration script. Load a saved file in its matching shell. The Zsh output is intended for explicit sourcing; copying it into system completion directories is unnecessary. Manually saved scripts do not update automatically: regenerate and reload them after upgrading, and open a new terminal to clear old completion definitions.

Both `hanamori` and `hanamori.exe` are registered, including the function installed by the hook. An executable outside PATH can still generate scripts when invoked by its path. Use a POSIX path understood by your shell in Windows Bash/Zsh.

## Local dynamic candidates

All three shells support these local candidates. The next Tab press reads changes after an installation, import or alias update without regenerating the script.

| Input position | Candidates |
| --- | --- |
| First positional argument of `use`, `default`, `alias` | Managed directory keys, external reference keys, existing aliases (including default), unambiguous full MSVC directory versions |
| Selectors for `exec --using`, `shell activate` | Same as above |
| `remove`, `unalias` | Existing named references |
| `uninstall` | Usable managed directory keys, managed references and unambiguous versions |
| `--dir PATH --toolset` | MSVC directory versions in the specified directory |
| `--dir PATH --sdk` | SDK directory versions in the specified directory; none with `--no-sdk` |

Directory version completion applies to `use`, `exec`, `import`, `env`, `shell activate` and `shell init`, including unregistered directories. These are actual installed versions such as `14.44.35207` and `10.0.26100.0`, not remote download IDs. The second argument of `alias` creates a new name and does not suggest selectors. Installation and remote catalog commands do not mix in local versions either.

When multiple installations share an MSVC version, for example with different SDKs, that version cannot select an installation uniquely. Completion offers exact directory keys and references instead. Activation candidates exclude unusable directories; remove/unalias can still suggest dangling references. Completion changes no files and does not replace execution-time checks.

Manager selection consistently follows the already entered `--manager-dir`, then `HANAMORI_HOME`, then the platform default (`%LOCALAPPDATA%\Hanamori` on Windows). Functions, direct executable calls and completion use the same rule. Changing HOME affects the next completion. A generation-time `--manager-dir` is not stored as a fallback manager.

`--using=prefix` and quoted/escaped paths are supported. Completion interprets literal arguments before the cursor without executing variable expansions or command expressions. Use `HANAMORI_HOME` when selecting a manager through such expressions.

Candidate lookup resolves `toolchains_dir` from CLI, environment, configuration and defaults. It does not parse unrelated proxy/log settings or project files, download manifests, write files or acquire locks. One malformed reference is skipped without hiding other installations. Unreadable storage suppresses relevant local candidates while static completion remains available. Manually saved scripts invoke the executable path used at generation time; regenerate them if you move the program.

## Supported completion

| Content | Behavior |
| --- | --- |
| Commands and options | Supported in PowerShell, Bash and Zsh, including nested commands such as `shell init`, `cache clean` and `self uninstall` |
| Fixed values | Bash/Zsh offer declared choices for options such as `--vs-version`, `--channel` and `--shell` |
| Files and directories | Bash/Zsh use path hints and shell filename completion; the shell handles spaces |
| PowerShell | Supports the local dynamic candidates above; fixed enum values and ordinary paths retain static-generator limitations, including context recognition with leading global options |
| Directory keys, aliases and installed versions | Scan managed directories, references or the explicit directory for the relevant input position |
| Remote toolset and SDK IDs | No network lookups; inspect `list-remote` instead |
| Arguments after `exec --` | No Hanamori option suggestions; completion of the child program's arguments is outside this feature |
| CMD / Fish | Not currently provided; requesting CMD completion returns an explicit error |

Suggestions do not replace command argument validation. Internal `shell dispatch`, `shell cmd-dispatch` and `shell run` commands are excluded.

## Removal and troubleshooting

`hanamori shell deinit` removes the managed startup block. `self uninstall` uses the same ownership records to clean it up. Loaded functions and completion remain in the current session until you restart the shell. Remove manually saved completion files and handwritten `source` entries yourself.

If no candidates appear, verify that you loaded the script for the correct shell and that your binary provides `completions`. In Zsh, initialize completion and reload the script if you see the `compinit` hint. For missing local candidates, check manager selection and diagnose directories and references with `list --json` / `doctor --json`; completion itself keeps these errors quiet. After an upgrade, regenerate manual scripts or open a new terminal using the startup loader.
