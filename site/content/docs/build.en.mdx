## One-command installation

Run in Windows PowerShell 5.1 or PowerShell 7 on Windows x64 / ARM64:

```powershell
irm https://hanamori.netlify.app/install.ps1 | iex
```

The script downloads the latest stable release, checks its SHA-256, size and reported version, and installs `%LOCALAPPDATA%\Hanamori\bin\hanamori.exe`. It adds the directory to your user PATH and initializes the current PowerShell profile and session with completions. It requires no administrator privileges and downloads no toolchains. Running inline takes effect immediately; running in a child process requires opening a new terminal afterward.

To choose a release or executable directory:

```powershell
& ([scriptblock]::Create((irm https://hanamori.netlify.app/install.ps1))) -Version 0.1.0 -InstallDir 'D:\Tools\Hanamori'
```

You can also set `HANAMORI_INSTALL_DIR` to the directory that should contain `hanamori.exe`:

```powershell
$env:HANAMORI_INSTALL_DIR = 'D:\Tools\Hanamori'
irm https://hanamori.netlify.app/install.ps1 | iex
```

The priority is `-InstallDir`, then `HANAMORI_INSTALL_DIR`, then `%LOCALAPPDATA%\Hanamori\bin`. An unset or empty environment variable uses the default directory.

| Parameter | Meaning |
| --- | --- |
| `-Version` | `latest` or a version, with an optional `v` prefix |
| `-InstallDir` | Directory containing `hanamori.exe` |
| `-NoPathUpdate` | Skip user and process PATH configuration |
| `-NoShell` | Skip persistent and current-session PowerShell integration |

Repeat installation replaces the executable and reuses existing configuration. Download or verification failures preserve the previous executable. `HANAMORI_HOME` still selects manager data, independently of the executable directory. Existing PATH entries and profile content are preserved. The installer warns about restrictive execution policies without changing them. Configure other shells through the [shell integration guide](/docs/shell).

Install toolchains when needed with `hanamori install latest --name stable`. Use `hanamori upgrade` for later updates and `hanamori self uninstall` for removal. The development version removes installer-owned PATH entries using the adjacent `.install.json` receipt; older executables may require manual PATH cleanup.

## MSYS2 and Git Bash

Run in MSYS2 or Git Bash on Windows x64 / ARM64:

```bash
curl -fsSL https://hanamori.netlify.app/install.sh | bash
```

The Bash installer reuses the PowerShell download, verification and user PATH setup, then invokes `hanamori shell init --shell bash` with the actual Bash runtime to configure `.bashrc`, login startup and completions. It defaults to `%LOCALAPPDATA%\Hanamori\bin`, installs no toolchains and leaves PowerShell profiles unchanged.

It requires `cygpath`, `curl` and Windows PowerShell or PowerShell 7. If PowerShell is absent from the MSYS2 PATH, the script checks the Windows system directory. From a checkout, run `bash install.sh` to use the adjacent `install.ps1`.

```bash
curl -fsSL https://hanamori.netlify.app/install.sh | bash -s -- \
  --version 0.1.0 --install-dir '/c/Tools/Hanamori'
```

Options are `--version`, `--install-dir`, `--no-path-update` and `--no-shell`. Installation directories accept MSYS or Windows paths. `--no-shell` skips Bash startup and completion setup; `--no-path-update` skips user PATH configuration.

Bash also supports `HANAMORI_INSTALL_DIR`, with `--install-dir` taking precedence. An unset or empty variable uses the default directory. For a piped installation, pass the variable to `bash`:

```bash
curl -fsSL https://hanamori.netlify.app/install.sh | HANAMORI_INSTALL_DIR='/d/Tools/Hanamori' bash
```

`curl | bash` runs in a child process. Open a new Bash terminal afterward, or run the printed hook command to use Hanamori immediately in the current terminal. MSYS2 may rebuild PATH at startup; the Bash hook invokes Hanamori by its absolute path.

## Build from source

```sh
git clone https://github.com/licyk/Hanamori.git
cd Hanamori
cargo build --locked --release -p hanamori --bin hanamori
```

On Windows the executable is `target/release/hanamori.exe`. No `aria2c`, `msiexec`, or
Visual Studio installation is needed to run the installer. Building requires Rust and a linker for the chosen target; the Windows MSVC target needs the corresponding build tools.
The repository is [licyk/Hanamori](https://github.com/licyk/Hanamori).

Build this revision from source. The existing release workflow produces
EXE and ZIP assets for `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`, named
`hanamori-<target>.exe` and `hanamori-<target>.zip`. The ZIP entry is `hanamori.exe`. These are intended artifact names, not evidence that this refactor
has been published. Historical assets do not establish support for the commands below.

## Portable installation

Use the [download page](/download) to find an actual matching release. Rename the standalone EXE to `hanamori.exe`, or extract it from the ZIP, and place it in a tools directory such as `D:\Tools\Hanamori`. No Rust installation is needed to run a downloaded executable.

For the current PowerShell session:

```powershell
$env:PATH = "D:\Tools\Hanamori;$env:PATH"
hanamori --version
```

For future sessions, add that directory to your user PATH through Windows Environment Variables. Shell initialization creates a command hook; it does not install the executable or permanently edit PATH.

A private repository requires access for cloning and downloading. The website does not provide credentials for private assets. Self-update supports the Windows x64 / ARM64 MSVC build; a different development target does not establish support for installing native MSVC on that host.

## ARM64 program builds

The installer chooses the native Windows architecture, including when launched from an emulated shell. Override with PowerShell `-Architecture x64` / `-Architecture arm64`, or Bash `--architecture x64` / `--architecture arm64`. This selects Hanamori itself; `hanamori install --arch HOST/TARGET` selects the compiler independently.

ARM64 releases provide `hanamori-aarch64-pc-windows-msvc.exe` and `.zip`; the ZIP contains `hanamori.exe`. Source builds use `cargo build --release --target aarch64-pc-windows-msvc` with the corresponding MSVC linker.
