The [Release workflow](https://github.com/licyk/Hanamori/blob/main/.github/workflows/release.yml) publishes both GitHub Release assets and the `hanamori` crate. Pushing a `v*` tag publishes to both channels. Manual runs let you choose a tag and a channel. Ordinary main pushes and website builds do not publish versions.

## Prepare a version and tag

Use the repository's `xtask` commands from the workspace or one of its packages:

```sh
cargo xtask bump          # Patch: 0.1.1 -> 0.1.2
cargo xtask bump minor    # Alternative: increment minor and reset patch
cargo xtask bump major    # Alternative: increment major and reset minor/patch
```

Choose one bump command. It updates `workspace.package.version` in `Cargo.toml` and uses
Cargo to regenerate the workspace entries in `Cargo.lock`, preserving locked dependency
versions. It does not commit changes or create tags. Commit the version change before tagging:

```sh
git add Cargo.toml Cargo.lock
git commit -m "chore: bump version"
cargo xtask tag --push
```

`cargo xtask tag` creates an annotated `vVERSION` tag at `HEAD` without pushing. The default
is the current workspace version, not the highest existing Git tag. An explicit version is
also supported, for example `cargo xtask tag 0.1.2 --push`; it must match the workspace version.
Tracked changes must be committed, and an existing tag is never replaced.

`--push` pushes only the created tag to `origin`, triggering both release channels. If the
push fails, the local tag is retained and the command prints the `git push` command to retry.

## Select a tag and channel

In Actions, choose **Release → Run workflow** and use the workflow on `main`:

| Input | Meaning |
| --- | --- |
| `tag` | An optional existing `v*` Git tag, such as `v0.1.0`. If omitted, the highest `v*` tag in Git version order is selected, independently of tag creation dates or GitHub Release dates. |
| `target` | `all` (default) publishes both channels; `github` publishes only GitHub Release assets; `crates-io` publishes only the crate. |

```sh
# Select the latest tag and publish both channels
gh workflow run release.yml --ref main

# Select the latest tag and publish only GitHub Release assets
gh workflow run release.yml --ref main -f target=github

# Publish an explicit existing tag to crates.io only
gh workflow run release.yml --ref main -f tag=v0.1.0 -f target=crates-io
```

The workflow does not create tags. Publication stops if there is no `v*` tag, the requested tag does not exist, or the tag version differs from the Cargo version in its source. A tag push selects that tag; an explicit manual `tag` input takes precedence.

## Checks, builds and publication

1. Update the workspace version and Cargo-generated lockfile, then create a `v*` tag pointing to the intended source.
2. Release fetches all tags, resolves the selected commit, and verifies its Cargo package name, version and binary target.
3. The reusable [CI workflow](https://github.com/licyk/Hanamori/blob/main/.github/workflows/ci.yml) and [Installers workflow](https://github.com/licyk/Hanamori/blob/main/.github/workflows/installers.yml) check Rust code and installer scripts separately at the same commit. Rust checks include formatting, module architecture and tests; installer checks cover arguments and metadata on Linux and native installation on Windows. Windows uses the release profile and `x86_64-pc-windows-msvc` / `aarch64-pc-windows-msvc` target.
4. After checks pass, the selected channels build and publish from the same commit. Ordinary branch CI does not respond to tag pushes; the two channels in one Release run share checks instead of running `cargo test` separately.
5. The GitHub channel builds on Windows x64 and `windows-11-arm`, packaging `hanamori-x86_64-pc-windows-msvc.exe`, `hanamori-aarch64-pc-windows-msvc.exe` and matching ZIPs containing `hanamori.exe`. All four published asset SHA-256 digests are verified.
6. The crates.io channel runs `cargo publish --locked`, retaining Cargo's compilation check of the packaged source. Only `hanamori` is published, not `hanamori-test-support` or `xtask`.

The two channels run independently after shared checks pass. If one fails, retry only the unpublished channel with the same tag. When manually publishing an older tag, checks and builds use that tag's source, not the main source that defines the workflow.

A passing CI run, website deployment or successful publication to one channel does not prove publication to the other. After a GitHub Release, also verify that users can download its assets. The download page and self-update use the asset names above; the page queries the public API without a token.

## crates.io credentials and retries

Configure `CARGO_REGISTRY_TOKEN` in the repository's Actions Secrets with a crates.io API token authorized to publish `hanamori`. The first publication requires permission to create the crate; subsequent publications require permission to publish that crate.

Run `cargo publish --locked --registry crates-io -p hanamori --dry-run` locally to compile the packaged source without uploading. A version already on crates.io cannot be overwritten. If the crate is already published and only GitHub assets are missing, select `target=github`.
